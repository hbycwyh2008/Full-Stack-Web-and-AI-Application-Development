# Weather App Evaluation Lab

**When:** After the selected CS6750 evaluation videos and after students have a clickable Figma Weather App prototype  
**Object:** The Weather App interface previously designed in Figma, based on the [Coursera guided project](https://www.coursera.org/projects/ui-design-using-figma-create-a-weather-app-interface)  
**Purpose:** Apply both heuristic evaluation and usability testing to one shared mobile-app prototype.

This lab evaluates the existing design. It is not another Figma build assignment. The teacher provides the current Figma prototype link and confirms which screens and interactions are actually connected before students write test tasks.

## Learning targets

Students can:

- inspect an interface against named usability principles and report a specific issue;
- test a goal with a user without coaching;
- keep **inspection predictions** separate from **observed user evidence**;
- recommend a design change supported by evidence.

## Before class — teacher check

- [ ] Share a viewable Figma prototype link.
- [ ] Test the prototype from its starting frame.
- [ ] List the screens and interactions that work.
- [ ] Choose a task that the prototype can actually support.
- [ ] If the prototype only displays a single weather screen, make the test about finding and interpreting its information; do not require navigation that is not built.
- [ ] If there is a connected flow, make the task exercise that flow.

Example task, only if supported by the current file:

> Starting from the opening screen, get to the weather information and tell me what you would prepare for going outside.

Do not tell students that the interface has a search, location switch, hourly forecast, or other feature unless that feature exists in the prototype.

## Part A — Heuristic evaluation

Work individually first, then compare findings with a partner. Inspect the prototype; do not ask a user to perform a task during this pass.

Use these six checks:

| Heuristic | Inspection question |
|---|---|
| **Affordance / signifier** | Is it clear which elements can be tapped or changed? |
| **Mapping** | Can a user predict what will happen after tapping a control? |
| **Constraints** | Does the interface prevent or help recover from likely mistakes? |
| **Visibility of system status** | Does the interface show the current location, weather state, or result clearly where relevant? |
| **Consistency and standards** | Do similar controls, labels, and visual patterns behave consistently? |
| **User control and freedom** | Can the user go back, change a choice, or recover from an unintended action where needed? |

Record only issues tied to a screen or interaction. A preference such as “I would use a different color” is not a heuristic finding by itself.

| Screen / interaction | Heuristic | Specific evidence in the design | Potential effect on the user | Priority |
|---|---|---|---|---|
| | | | | Must / Should / Later |
| | | | | Must / Should / Later |
| | | | | Must / Should / Later |

Label this section **inspection finding**. It predicts a possible usability problem; it does not prove that a user experienced it.

## Part B — Usability test

Use a peer who did not design the Weather App. Give them the teacher-approved goal-based task, not step-by-step directions.

1. Start the prototype at the agreed starting frame.
2. Read the task once. Do not point, coach, or explain the interface.
3. Observe the user's actions and pauses.
4. If the user asks for help, record the question and any help given.
5. After the task, ask: **“What did you expect to happen?”**

| Check | Observation |
|---|---|
| Completed the task independently? | |
| Wrong turn or repeated action | |
| Pause / hesitation and where it happened | |
| Help requested / help given | |
| Exact words that show expectation or confusion | |
| Screen or prototype fault, if any | |

Write what happened, not a guess about what the user was thinking.

- **Observable:** “The tester tapped the weather icon twice, then asked, ‘Is this the forecast?’”
- **Interpretation to test:** “The icon label may not make its purpose clear.”

Label this section **user-test observation**. Keep it separate from the heuristic inspection table.

## Part C — Synthesize

Choose the three most useful findings. Include at least one from each method.

| Method | Finding | Supporting evidence | Proposed change | Priority |
|---|---|---|---|---|
| Heuristic inspection | | | | Must / Should / Later |
| Usability test | | | | Must / Should / Later |
| Either method | | | | Must / Should / Later |

Priority definitions:

- **Must:** blocks the task or creates a serious failure;
- **Should:** causes avoidable confusion or effort;
- **Later:** low-impact refinement.

Finish with:

> **The inspection predicted ______. During the test, the user ______. We recommend changing ______ because ______.**

If a change is made, retest the same goal and record what changed. Do not claim the design improved until there is retest evidence.

## Method reminder

**Heuristic evaluation** is an expert/peer inspection against principles.  
**Usability testing** observes a user trying a realistic goal.  
One method can suggest a problem; the other can show how a user actually responds.
