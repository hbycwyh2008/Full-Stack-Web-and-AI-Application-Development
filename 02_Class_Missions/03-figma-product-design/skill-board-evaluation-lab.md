# Evaluation Lab — Morgan's Skill Board

**Order:** Learn the two evaluation methods → evaluate the shared Skill Board → apply the methods to your own prototype → revise/retest.
**Purpose:** Practice evidence-based evaluation of an existing product. This is not the Figma tool exam.

The teacher provides the actual Skill Board URL, suitable access and test data in class. No URL or product feature is assumed here. Use a teacher-approved test account; avoid changing real student progress or personal records. Use observation/inspection for actions that cannot safely be exercised.

## Learn the Two Methods

| Method | Who / action | Evidence |
|---|---|---|
| Heuristic Evaluation | A trained peer inspects the interface against named principles | Location, principle, problem and likely impact |
| Usability Testing | A representative user attempts a realistic task | Actions, errors, pauses, exact words, completion and assistance |

## Prepare Before the Test

Suggested classroom first round: 2–3 core tasks, three participants per team, around 10–15 minutes per participant, spread across meetings if needed. This is a small qualitative exercise, not a statistically reliable benchmark or a universal participant-count rule.

- Recruit users matching Skill Board's intended audience. Classmates are appropriate only when their role/needs match; otherwise they are practice participants and that limitation is recorded.
- Use roles: facilitator, participant, observer. The participant works individually and has not been taught the tested navigation path.
- The teacher defines actual task goals and observable success criteria in advance. Do not ask students to invent first-use test tasks by exploring the same interface they will then test.
- Tell the participant that the interface is being evaluated, not their ability; explain the prototype/test-account boundaries and ask them to say what they are looking for or expecting.
- Check links and test accounts before participants arrive. Do not collect unnecessary identifying information or make recordings without appropriate agreement.

## Pass A — Usability Testing

For participants doing both activities, test **before** they inspect the interface for heuristic problems. If classmates have already inspected it, recruit a fresh participant for first-use testing. Teach the method on a different example beforehand.

1. Give one task at a time, without explaining the UI.
2. Observe. A neutral prompt is “What are you looking for now?” Avoid “Click the button at the top.”
3. Record help, errors and actual behavior. If assistance is needed, give it and record the result as assisted.
4. Ask a short follow-up after the task: “What did you expect to happen there?”
5. Reset using the agreed start state for the next participant.

## Synthesize and Retest

| Priority | Meaning |
|---|---|
| MUST | Blocks the main task or creates a serious failure |
| SHOULD | Causes repeated hesitation, errors or unnecessary effort |
| LATER | Low-impact refinement |

For each proposed revision, record **location → evidence or inspection rationale → impact → proposed change**. Submit recommendations for Morgan's Skill Board; do not alter the live product. For your own prototype, implement the change and record **before → evidence → change → retest result**. A fresh participant is preferable for first-use claims; note any repeat-user familiarity.

Submit the two tables, task plan, prioritized findings and retest plan/result. Figma skill score, heuristic inspection quality and user-testing quality are separate evidence categories.
