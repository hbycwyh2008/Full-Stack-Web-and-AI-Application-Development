## Part A — Prototype Purpose + Fidelity (6 pts)

### 1. — 2 pts

Expected:

- team is investing in fidelity/polish before validating the main interaction;
- prototype should answer an important question cheaply before expensive refinement.

### 2. — 2 pts

**B**

A simple low-fi flow is sufficient to test step order and is faster/cheaper to revise.

### 3. — 2 pts

- 1 pt: writes a testable task outcome.
- 1 pt: names a limitation such as visual-brand quality, final performance, production behavior, or realistic edge cases.

---

## Part B — Core 3 (6 pts)

### 4.

**Affordance / signifier** — the clickable element does not signal that it is actionable.

### 5.

Primarily **Mapping** — action → result is unclear. Accept feedback-related reasoning if the student clearly explains the missing action/result relationship.

### 6.

**Constraints** — the interface allows an invalid/incomplete submission and gives poor recovery.

2 pts each: correct principle + sound explanation.

## Part C — Evaluation (8 pts)

### 7. — 2 pts

Strong example:

> “Add tomorrow's science homework and make sure it has been saved.”

Must state the goal without revealing clicks.

### 8. — 2 pts

Coaching changes the user's behavior and hides where the interface itself fails.

### 9. — 2 pts

- **E** tester tapped wrong icon twice
- **T** interface looks boring
- **E** “Where do I save?”
- **A** students will obviously understand

0.5 pt each.

### 10. — 2 pts

Accept any revision tied to the evidence.

Example:

> SHOULD: make the assignment entry/navigation label more visible and specific because the participant paused 8 seconds, opened the wrong screen, and asked where the assignment was.

---

## Part D — Iterate + Retest (5 pts)

### 11. — 3 pts

> **Evidence → Design problem → Change → Retest / result**

Retest is necessary because a change is only a hypothesis; it may not actually improve task performance.

### 12. — 2 pts

The change is not connected to the failure evidence. The problem was label clarity, not color preference. The team changed appearance rather than the observed interaction problem.

---

## Part E — Practical Figma Mini-Task (5 pts)

Award 1 point each:

- [ ] two screens/states exist;
- [ ] first screen supports the stated add-homework task;
- [ ] second screen communicates success;
- [ ] primary action is connected/clickable;
- [ ] main action has a clear signifier and the design remains appropriately low-fi.

Do not grade visual polish.

# Score Interpretation

| Score | Interpretation | Next step |
|---|---|---|
| **27–30** | Secure mastery | Ready for HTML/CSS implementation |
| **23–26** | Mostly secure | Fix targeted misconception/skill gap |
| **18–22** | Partial mastery | Re-teach + short reassessment |
| **0–17** | Not yet secure | Revisit Prototype → Evaluate → Iterate |

## Non-negotiable practical gate

Regardless of total score, the student should revise before implementation if they cannot:

- connect a simple Figma interaction;
- write a goal-based usability task;
- distinguish observed evidence from personal taste;
- explain why a revision follows from evidence.
