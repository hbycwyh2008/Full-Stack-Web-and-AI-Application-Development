# Lesson 26 — GitHub Pages Release and Maintenance

## Mission
Ship a stable version, document it, and decide what to learn from after release.

## Core Artifact
Deployed site + tagged/versioned release notes + maintenance plan.

## Launch Challenge — 0–10
Compare “project is done” with a real release checklist. Students identify what could still fail after local development appears complete.

## Evidence / Resource Scan — 10–25
Check current `main`, open issues, acceptance criteria, links/assets, responsive behavior, accessibility, and deployment configuration.

## Team Sensemaking — 25–40
Teams decide release blockers versus acceptable known limitations. Record the rationale.

## Studio Build — 40–65
Deploy the static site using GitHub Pages or the approved class deployment path. Create release notes containing user-facing changes, fixes, known limitations, and test evidence.

## Critique / Test — 65–80
A different device/browser/user opens the deployed URL and runs the primary task from scratch. Any production-only failure is logged.

## Ship Evidence — 80–90
Fix blockers or record them honestly. Publish the release and write a maintenance plan: **what feedback/data would justify the next iteration?**

## Success Evidence
Students understand release as another lifecycle stage, not the end of learning.
