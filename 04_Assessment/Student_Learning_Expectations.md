# Student Learning Expectations

This course is not a typing-along exercise. Students are expected to build real habits of evidence, design, programming, debugging, testing, collaboration, and reflection.

## Core Expectation

A working product is not enough if the student cannot explain how it was researched, designed, implemented, tested, and revised.

## 1. Computer Science Is More Than Coding

Students should connect programming work to larger CS ideas: computation, information, algorithms, abstraction, systems, HCI, software engineering, AI, and impacts.

## 2. Evidence Before Assumption

When user evidence, tests, code behavior, or Git history can answer a question, decisions should not rest only on preference.

Students should distinguish:

- observation from interpretation;
- requirement from feature idea;
- expected from actual behavior;
- AI capability from unsupported inference.

## 3. Explain and Modify Code

Students should be able to trace important JavaScript, explain input/state/processing/output, identify functions/data structures/control flow, and modify the program when a requirement changes.

Copying code or accepting generated code without understanding does not meet the standard.

## 4. Debug Systematically

Use:

```text
reproduce
→ observed vs expected
→ hypothesis
→ experiment/evidence
→ fix
→ verification/regression check
```

Students should attempt diagnosis using errors, logs, dev tools, documentation, prior evidence, or tests before outsourcing the problem.

## 5. Use GitHub as Development Evidence

Issues, branches, commits, pull requests, reviews, and releases should show how the product changed. One final upload is not a development history.

## 6. Test and Revise

Students should expect designs and code to change after critique, user testing, code review, accessibility checks, and QA. Revision is evidence of learning, not evidence that the first attempt failed.

## 7. Use AI Responsibly

Generative AI may support explanation, hints, debugging, feedback, or practice when allowed by the course policy. Students remain responsible for:

- reading and understanding output;
- testing claims/code;
- revising work;
- disclosing assistance when required;
- being able to explain the final result independently.

## 8. Oral Explanation

Teachers may ask students to explain a design decision, trace code, reproduce a bug, justify a requirement, interpret research evidence, or describe how AI assistance was used. This verifies student understanding.

## What Strong Work Looks Like

A strong student can:

- explain why the product exists;
- show how evidence shaped requirements/design;
- read and modify their own code;
- debug with a hypothesis rather than random edits;
- review another student's work constructively;
- test with users and technical checks;
- show revisions in GitHub/Figma;
- discuss AI with explicit evidence and limitations;
- transfer the process to a new project.
