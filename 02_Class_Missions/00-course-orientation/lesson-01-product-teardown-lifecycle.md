# Lesson 01 — Product Teardown: Trace the Software Lifecycle

**Prerequisite:** Required Four-Poster Orientation + Lesson 00  
**Length:** 90 minutes  
**Mission:** Reverse-engineer the likely development decisions behind an existing website or app and recognize that implementation is only one stage of software development.  
**One Required Resource / Evidence Source:** one familiar live website/app or teacher-provided screenshots  
**Durable Evidence:** `research/product-teardown.md`

---

## 0–10 min — Entry Point Check

Work individually.

Choose one familiar digital product and record:

- three visible interface decisions;
- the user problem you think each decision is trying to solve;
- one thing you cannot know just by looking at the finished product.

Mark each claim as **Observation / Inference / Unsure**.

---

## 10–25 min — Individual Learning

Use only the live product/screenshots as today's required evidence source.

Inspect and record examples of:

- navigation;
- feedback to the user;
- error prevention/recovery;
- accessibility;
- information/data collection;
- signs that the product has been revised over time.

For each observation, write one development question that must have existed before or after coding.

Examples of question types: user need, requirement, design, implementation, testing, release, maintenance.

---

## 25–40 min — Talk Round 1

In pairs, compare observations.

Classify evidence under:

- research;
- requirements;
- design;
- implementation;
- testing;
- release;
- maintenance/iteration.

Find:

- one observation that fits clearly into one stage;
- one observation that could connect to multiple stages;
- one claim that is still only an assumption.

Be prepared to defend the classification with product evidence, not with teacher approval.

---

## 40–55 min — Entry Points Check / Teacher Diagnosis

Groups of 3–4 build a **Lifecycle Evidence Map** using the sequence:

```text
discover → research → define → design → plan → build → review/test → release → learn → iterate
```

Place the team's strongest product evidence onto the map.

Then place these course tools/practices where they most strongly contribute:

- HCI research;
- Figma;
- GitHub;
- HTML/CSS/JavaScript;
- usability testing.

Groups display:

1. one placement they are confident about;
2. one placement they debated;
3. one missing stage for which the finished product gives little/no direct evidence.

### Teacher diagnosis

Clarify only common misconceptions. Emphasize that the lifecycle is **iterative**, not a rigid one-way waterfall, and that coding/building is central but not the entire process.

---

## 55–75 min — Guided Practice / Mission Task

Create `research/product-teardown.md` with:

- product name and target users;
- likely user goal/problem;
- three observations separated from assumptions;
- three inferred requirements;
- two design decisions;
- one implementation challenge;
- two tests the team would run;
- one release/maintenance concern;
- one improvement hypothesis;
- a lifecycle diagram showing at least one feedback loop.

For every inference, include the evidence that led to it or label it explicitly as a hypothesis.

---

## 75–85 min — Exit Check

Work individually.

A new product team says:

> “We already know the app idea. We should just start coding.”

Write a short response that identifies **at least three lifecycle stages** that could reduce the risk of building the wrong thing.

Then complete:

> **Before this lesson, I saw software mainly as ____________________. Now I see ____________________.**

---

## 85–90 min — Submission

Submit/commit:

1. individual Entry Point notes;
2. group Lifecycle Evidence Map;
3. `research/product-teardown.md`;
4. individual Exit Check.

## Success Evidence

Students can:

- distinguish observations from assumptions;
- explain multiple stages of the software lifecycle;
- place HCI, Figma, GitHub, coding, and testing into a coherent iterative process;
- explain why “start coding immediately” can create product risk.
